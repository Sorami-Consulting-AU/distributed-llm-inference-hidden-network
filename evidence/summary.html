The Hidden Network: Ray control-plane exposure in one tested KubeRay and vLLM topology

Experiments 2026-09-28 (UTC), Amazon EKS 1.35, ap-southeast-2. Report built 2026-09-29.  Sorami Consulting. Corrections after independent review applied 2026-09-29.

Data companion to the Sorami Technical Report at sorami.com.au/research/distributed-llm-inference-hidden-network/ (markdown copy for reproducibility: the report on sorami.com.au). Every benchmark number and port count below is computed by the evidence build from the raw logs and result-c*.json files; the script exits with an error if the report text disagrees with the raw data.

Key findings
  1. OBSERVED 15 of 17 Ray listening sockets seen from a neighbour pod were absent from the pods' declared containerPort metadata, and four default scanner configurations made zero references to the RayCluster. This is visibility drift, not a Kubernetes bypass.
  2. OBSERVED Ray GCS and raylet accepted cleartext gRPC from an unrelated namespace. An ingress-only default-deny NetworkPolicy (L1) turned all 7 ports open at L0 into BLOCKED from that neighbour; egress was left open, so it shows no containment of a compromised engine.
  3. OBSERVEDDOCUMENTED The engine API key (L3) returned 401 for ordinary requests on two /v1 routes. It is not authentication closure: the other routes were untested and vllm/vllm-openai:v0.11.0 is in the CVE-2026-48746 bypass range (bypass not tested).
  4. OBSERVED Cilium chaining plus WireGuard (L2b, combined) carried 512 of 512 streaming requests, with 3.4% to 6.5% lower throughput and +3.2% to +8.4% median E2E vs a same-session bracket in this single bracketed run (n=1; low concurrency within drift; closing bracket not proven Cilium-free).
  5. OBSERVED The tested Linkerd mTLS configuration (L2a) served 0 of 512 requests (HTTP 503 at every level). The root cause was not isolated, so this is not a Linkerd incompatibility claim.

0. Run timeline

1. Attack surface

  • OBSERVED 15 of 17 Ray listening sockets seen from the neighbour in Stage A were absent from declared containerPort metadata (10 of 11 head, 5 of 6 worker).
  • DOCUMENTED containerPort is informational; Kubernetes does not block undeclared ports. The finding is visibility drift for reviewers and port-based tooling.
  • OBSERVED Four default scanner configurations (Trivy, Checkov, Kubescape, kube-linter) reported 31, 20, 1 and 5 findings with zero references to the RayCluster resource. Custom rules were not tested.
  • OBSERVED Ray GCS 6379 and raylet 10002 answered with a cleartext HTTP/2 SETTINGS frame; a TLS ClientHello failed with WRONG_VERSION_NUMBER.
  • NOT TESTED Decoding gRPC messages, capturing the NCCL activation stream, and whether GCS/raylet access alone can schedule work.

L1 NetworkPolicy (ingress only)

  • OBSERVED All 7 Ray ports open at L0 (6 head, 1 worker) were BLOCKED from the neighbour after L1; 8000 stayed open by design.
  • OBSERVED The policy is ingress-only: policyTypes: ["Ingress"] at line 22 of manifests/stageD-L1-networkpolicy.yaml, with egress deliberately left open (comment at line 11). It does not show containment of a compromised engine.
  • DOCUMENTED VPC CNI NETWORK_POLICY_ENFORCING_MODE=standard (the default) starts new pods default-allow until policies are programmed; strict starts default-deny [S5].
  • NOT TESTED The enforcing-mode value was not recorded (only the variable name is in the logs), so the startup window is unmeasured. Egress was not tested.

L2b Cilium chaining + WireGuard

  • OBSERVED 512 of 512 streaming requests succeeded. A 55.19 MB head-to-worker transfer grew head cilium_wg0 tx by 55.79 MB; over the sweep head cilium_wg0 tx grew 572.5 MB.
  • INFERRED Inter-node pipeline traffic was encrypted: the evidence is agent status, peers, handshakes and interface counters, not a ciphertext packet capture on the ENI.
  • OBSERVED An incomplete Cilium removal procedure, uninstalling with the documented chart default cni.uninstall=false, left 05-cilium.conflist on every node and broke new pod sandboxes from about 12:41Z to 13:09Z. This is a procedure gap, not Cilium misbehaving.

4. Threats to validity (short form)

  • OBSERVED n=1 run per level; no raw per-request samples persisted, so no distributions, confidence intervals or outlier analysis.
  • OBSERVED L0 for L1 and L3 is the reused Stage C run (cross-session). L2b ran on different GPUs (2 x A10G) from L0/L1/L3 (A10G + T4).
  • OBSERVED L0-after is not a proven Cilium-free baseline: Cilium agent running with encryption off until 13:22:22Z, worker endpoint state not checked.
  • OBSERVED The L2b difference is Cilium chaining plus WireGuard combined; the Cilium-only share was not isolated.
  • OBSERVED Images were tag-pinned, not digest-pinned; Linkerd and Checkov versions were not recorded. Small model (Qwen2.5-1.5B), short prompts, one region, one day.

5. Future work

  1. Route-by-route authentication matrix across vLLM versions. Enumerate every route from /openapi.json and call each with no key, a wrong key, and the correct key, on v0.11.0, a patched release (0.22.0 or later), and each behind an RFC-conforming proxy. Reproduce the CVE-2026-48746 regression only in an isolated environment. Classify each route as inference-capable, administrative, or information-disclosing.
  2. Ray native security versus network controls. A factorial of Ray token authentication (RAY_AUTH_MODE=token) and Ray TLS, crossed with NetworkPolicy and WireGuard, measuring both security effect (rejection, handshake behaviour, reachability) and serving difference (throughput, TTFT, TPOT, E2E, CPU).
  3. VPC CNI startup-window measurement. Probe a newly created target pod continuously from an unrelated namespace while recording sandbox creation, PolicyEndpoint programming, and Ready state; repeat many times under NETWORK_POLICY_ENFORCING_MODE=standard and under strict, and report the exposure-window distribution. No GPU needed.
  4. A/B/C Cilium decomposition. A: plain VPC CNI. B: Cilium chained with encryption disabled (with agents restarted and the state confirmed on every engine pod). C: the same Cilium plus WireGuard. Randomise the order across at least 10 blocks on identical nodes so that B minus A estimates the datapath difference and C minus B estimates the incremental WireGuard difference, with confidence intervals over blocks.
  5. Egress tests. Add egress NetworkPolicy and test outbound reach from a compromised-engine vantage point (other namespaces, instance metadata, the internet, model stores).
  6. Digest-pinned artifact manifest. Record runtime image digests, chart digests, model and tokenizer revisions, scanner, Linkerd, Cilium, kernel, driver and CNI versions in one machine-readable manifest with SHA-256 sums, and keep the harness under version control.
  7. Persist raw samples. Change the bench Job so the full {"summary","raw"} file leaves the pod (print it, or write it to a volume), so every run keeps per-request TTFT, TPOT and E2E for distributions, bootstrap intervals, and stall analysis.
  8. Linkerd root cause. Repeat L2a with a pinned Linkerd version, kept proxy logs, and a controlled split of Service versus pod-IP targeting, protocol detection versus opaque ports, and one-sided versus two-sided meshing. This is an engineering question, not a security one.
  9. What the exposed Ray ports allow beyond reachability. Not tested: whether a client with network access to GCS and raylet alone can read cluster state, schedule work or execute code on the GPU inference deployment. This needs an approved, isolated experiment.
  10. Ray native authentication and NetworkPolicy together. Not tested: whether NetworkPolicy is still needed when Ray token authentication or TLS is configured, and what each closes on its own (see item 2).
  11. Scanner fairness. Not tested: the same manifests with custom rules, with admission-time policy engines that render custom resources, and with scanners that parse the RayCluster resource, so that a like-for-like comparison of runtime-exposure detection is possible. The comparison in Section 5.1 is not like for like.
  12. Newly created Ray pods during startup. Not tested (see item 3): probe pods created after the policy exists, with the enforcing mode recorded first.
  13. Job API and code execution on the GPU stack. Not demonstrated. If the Job API is enabled in a GPU deployment, test it only in an isolated environment with the same safe-probing rules.
